# Security policy

Pinga53 sits in your DNS path, so we take security reports seriously.

## Reporting

Please report vulnerabilities **privately** through GitHub:
**Security → Report a vulnerability** on
<https://github.com/dubyfls/Pinga53>. Do not open a public issue.

Include what you found, how to reproduce it, and the version
(`scamwall version`). You should hear back within 7 days.

## Supported versions

Pinga53 is alpha. Only the latest release gets fixes.

## Design notes

- The ScamWall engine runs as an unprivileged `scamwall` user. Only the
  zone installer runs as root, and it validates the zone
  (`named-checkzone`, size and change caps, protected names) before
  Unbound sees it.
- Fetchers only download. They never send your queries, clients or
  allow list anywhere.
- Evidence is signed with a key generated on your machine. The private
  key never leaves it.
- API keys live in `/etc/pinga53/scamwall/secrets/` (root:scamwall, 0640)
  and are redacted from logs and errors.

## Dashboard (v0.2.0-alpha)

- The dashboard runs as a dedicated non-root `pinga53` user, under a
  hardened systemd unit (`NoNewPrivileges`, `ProtectSystem=strict`,
  no capabilities, writable paths restricted to its own state and the
  TLS directory).
- **Authentication:** Argon2id password hashing (passlib), TOTP MFA via
  pyotp with replay protection (the TOTP step used to log you in cannot
  be replayed to authorize an admin action), ten single-use recovery
  codes, and a per-IP sliding-window rate limit on `/api/auth/login`.
- **Session:** short-lived JWT (8h) signed with `PINGA53_SECRET_KEY`
  (>=32 chars, generated by `install.sh` with `openssl rand -hex 32`).
  Tokens are kept in `sessionStorage` on the client (gone on browser
  close), and the server strips `Server:` headers.
- **Forced-flow gate:** every authenticated route refuses with
  `409 must_change_password` or `409 must_enroll_mfa` until the account
  owes neither, so a bootstrap password cannot be used to call anything
  but the password-change and MFA-setup routes.
- **Audit log:** append-only, hash-chained. Every mutation is recorded
  with the actor, timestamp, and inputs (never the secret or TOTP code).
  `pinga53d audit-verify` re-walks the chain.
- **ScamWall owner actions** (toggle mode, pause automatic blocking,
  add/remove protected host, run-now) require admin + a fresh TOTP
  step-up (a *new* code; the one that logged you in won't work) and are
  dispatched through a tiny root helper, `/usr/local/sbin/pinga53-helper`:

  - setuid-free; invoked by the `pinga53` user through a sudoers drop-in
    (`/etc/sudoers.d/pinga53-dashboard`) that whitelists exactly this one
    binary for exactly this one user;
  - its subcommand set is a fixed allowlist of seven entries. Anything
    outside the allowlist is refused with a usage message;
  - host arguments are validated against a strict regex (lowercase IDNA
    labels, no control chars, no whitespace, <=253 chars) *and* again by
    the helper, so neither the API nor the helper trusts the other;
  - `install.sh` validates the sudoers drop-in with `visudo -cf` before
    dropping it into `/etc/sudoers.d/`, so a broken rule can't lock you out.

- **TLS:** first-start generates a self-signed ECDSA P-256 certificate in
  `/etc/pinga53/dashboard/tls/`, mode 0600 for the key, owned by the
  service user. SANs cover the system hostname and non-loopback IPv4
  addresses. Operators who have a real certificate point
  `PINGA53_TLS_CERT` / `PINGA53_TLS_KEY` at their own files.
- **Pi-hole app password:** supplied once at install into
  `/etc/pinga53/dashboard.env` (mode 0640, root:pinga53). Never prompted
  for in the browser; never logged.
